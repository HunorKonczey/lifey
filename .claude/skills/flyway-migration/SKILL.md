# Flyway migration

Every schema change ships as a new migration file. `spring.jpa.hibernate.ddl-auto`
is `validate`, so the migration and the JPA entity must describe exactly the
same schema — a mismatch stops the application from starting, on every
environment at once.

## 1. Pick the version number

```bash
ls backend/src/main/resources/db/migration | sed -E 's/^V([0-9]+)__.*/\1/' | sort -n | tail -1
```

Next version is that number **+ 1**. The sequence has a gap (there is no `V64`);
**never fill a gap** — a number that may already exist in someone's
`flyway_schema_history` is not free to reuse.

File name: `V<N>__<snake_case_description>.sql`, two underscores after the
version. The description names the change, not the feature epic:
`V67__cardio_details.sql`, `V69__cardio_best_efforts.sql`,
`V71__cardio_hike_fields.sql`.

## 2. Never edit an applied migration

Once a migration exists on `main` it may have run against a real database.
Changing it changes its checksum and Flyway refuses to start. Fix a mistake by
adding the next migration.

## 3. Write it in the house style

Lowercase SQL. A comment header explaining **why**, citing the plan doc that
decided it — this is a strong convention in this repo and the migrations are
much more readable for it:

```sql
-- Best-effort sub-distances for a running session (docs/cardio/60 C6.1,
-- docs/cardio/56 D-C3.8): the fastest continuous 1/5/10 km inside the
-- session, NOT the average pace extrapolated over those distances.
--
-- Nullable: a treadmill run or a run shorter than the window leaves them
-- null (null, never 0 — 0 would read as an impossibly fast record).
alter table cardio_details
    add column best_1k_seconds  integer,
    add column best_5k_seconds  integer,
    add column best_10k_seconds integer;
```

Types and shapes in use:

| Thing | Write it as |
|---|---|
| Primary key | `id bigint generated by default as identity primary key` (`bigserial` also appears in older files — match the neighbours in a table you are extending, prefer identity for new tables) |
| Timestamps | `timestamptz` — never bare `timestamp` |
| Money-free reals | `double precision` |
| Short enums / codes | `varchar(16)` or `varchar(32)` + a check constraint |
| Owner column | `user_id bigint not null references users (id) on delete cascade` |
| Child rows | `references <parent> (id) on delete cascade` |

Name every constraint you add: `<table>_<what>_ck` for checks,
`<table>_<cols>_unique` for uniques. An unnamed constraint gets a generated
name that the next migration cannot reference.

## 4. Indexes

**Postgres does not index foreign-key columns automatically.** Every FK column
you add gets an index in the same migration:

```sql
create index meal_entries_meal_id_idx on meal_entries (meal_id);
```

Naming: `<table>_<column>_idx` (the dominant form; `idx_<table>_<column>` also
exists in older delta-sync migrations — match what's already on the table).

## 5. Ownership and delta-sync columns

A business entity table needs a `user_id` (see the two rules in the
`backend-feature-slice` skill). If the mobile app caches the entity offline,
the table also needs the delta-sync pair, matching `SyncableEntity`:

```sql
alter table foods add column updated_at timestamptz not null default now();
alter table foods add column deleted_at timestamptz;

create index idx_foods_updated_at on foods (updated_at, id);
```

The composite `(updated_at, id)` index is not optional — it is exactly the sort
order the delta feed pages by.

`updated_at` is maintained by JPA lifecycle callbacks, not a DB trigger. That
holds only while every write goes through JPA: if you add a raw-SQL or batch
write path to a synced table, it must bump `updated_at` itself or the mobile
clients will never see the change.

## 6. Adding a NOT NULL column to a populated table

Three safe shapes, in order of preference:

1. **Nullable, and teach the code to handle null.** Best when "not set" is a
   real state.
2. **`not null default <value>`** — Postgres 11+ rewrites no rows, so this is
   cheap even on a large table. Right when a sensible default exists.
3. **Three statements in one migration**: add nullable → `update` to backfill →
   `alter column ... set not null`. Use when the value must be derived per row.
   Say in the comment header what the backfill assumes.

Never add a bare `not null` column without one of these — it fails on any table
that already has rows.

## 7. Forbidden tables

A backend migration must not name `chat_conversations`, `chat_messages`,
`chat_participants`, or `chat_message_attachments` — they belong to the
`lifey-chat` service and its own migration directory. `V65`-style columns on
`user_settings` are fine; the table is the monolith's.

## 8. Verify

```bash
./devops/check-schema-ownership.sh && cd backend && ./mvnw -B verify
```

`verify` runs Flyway against a Testcontainers Postgres (Docker must be running)
and then Hibernate's `validate` — which is what catches "the migration says
`double precision`, the entity says `Integer`" before it reaches an
environment. A migration that has not been run this way has not been tested.

## Checklist

- [ ] Version = highest existing + 1, no gap filled, `V<N>__<snake_case>.sql`
- [ ] No existing migration edited
- [ ] Comment header says why, citing the plan doc
- [ ] `user_id ... on delete cascade` for a business table
- [ ] Index on every new FK column
- [ ] `updated_at`/`deleted_at` + `(updated_at, id)` index for a synced entity
- [ ] Constraints named
- [ ] NOT NULL on an existing table uses a default or a backfill
- [ ] Entity and migration describe the same schema
- [ ] Ownership check + `./mvnw -B verify` clean
